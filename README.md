# CS2 Highlight Cutter — веб-интерфейс

Статический фронтенд для сервиса нарезки хайлайтов CS2. Одна страница плюс
файл с адресом бэкенда — ни сборки, ни зависимостей, ни Node.

Рендер живёт в отдельном репозитории (`cs2_cutter`): там CS2, GPU, виртуальная
сессия и запись. Здесь только интерфейс, поэтому этот репозиторий можно
разворачивать на любой машине — GPU и игра ей не нужны.

```
    ┌─ UI-хост ───────────────┐          ┌─ Рендер-хост ───────────────────┐
    │  serve_ui.sh :8080      │ ──API──► │  cs2_cutter :8000               │
    │  web/ + config.js       │          │  CS2_SERVE_UI=0 (только /api/*) │
    │  (ни GPU, ни CS2)       │          │  sway + Steam + CS2 + GPU       │
    │                         │          └─────────────────────────────────┘
    │                         │          ┌─ Библиотека ────────────────────┐
    │                         │ ──API──► │  cs2_cutter_backend :8000       │
    │                         │          │  авторизация + фрагменты        │
    └─────────────────────────┘          └─────────────────────────────────┘
```

UI ходит в два сервиса: нарезка и запись — на рендер-хосте, авторизация и
библиотека фрагментов — в `cs2_cutter_backend`. Разделение не косметическое:
рендер-хост занят CS2 и GPU, его перезапускают, а библиотека должна
открываться и когда игра не запущена. Когда бэкенды сольют в один, второй
адрес можно просто не задавать.

## Запуск

```bash
CS2_API_BASE=http://192.168.0.4:8000 CS2_LIBRARY_BASE=http://192.168.0.5:8000 ./serve_ui.sh
CS2_API_BASE=http://192.168.0.4:8000 UI_HOST=127.0.0.1 ./serve_ui.sh   # библиотека там же
```

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `CS2_API_BASE` | пусто | адрес рендер-бэкенда; пустой = тот же origin (для отдельного UI это ошибка, скрипт предупредит) |
| `CS2_LIBRARY_BASE` | пусто | адрес сервиса авторизации и библиотеки; пустой = там же, где `CS2_API_BASE` |
| `UI_HOST` | `0.0.0.0` | интерфейс, на котором слушать |
| `UI_PORT` | 8080 | порт UI |

Статику отдаёт `python3 -m http.server` — для одной страницы этого достаточно, и
зависимостей не требует. Перед запуском скрипт генерирует `web/config.js` из
`CS2_API_BASE`.

Как systemd-юнит пользователя (адрес бэкенда правится в `Environment=CS2_API_BASE`):
```bash
cp systemd/cs2-cutter-ui.service ~/.config/systemd/user/
systemctl --user daemon-reload && systemctl --user enable --now cs2-cutter-ui
loginctl enable-linger $USER
```

## Откуда UI берёт адрес бэкенда

Сверху вниз, первое непустое побеждает:

| Источник | Когда удобен |
|---|---|
| `?api=http://host:port` в URL | разово ткнуться в другой бэкенд; запоминается в localStorage, `?api=` без значения сбрасывает |
| localStorage | ранее выбранный оверрайд |
| `window.CS2_API_BASE` в `web/config.js` | настройка развёртывания; генерируется `serve_ui.sh` |
| пусто | тот же origin |

Адрес библиотеки берётся так же (`?lib=…` → localStorage → `window.CS2_LIBRARY_BASE`),
а если не задан — совпадает с адресом бэкенда.

Текущие адреса видны в шапке UI, а если бэкенд не отвечает — там же будет
`бэкенд недоступен: <адрес>`, чтобы не гадать, что именно молчит.

`web/config.js` в репозиторий не входит (он в `.gitignore`): это параметр
конкретной установки, а не общего кода. В репозитории лежит `config.example.js`.
Если открыть `web/index.html` файлом, без `serve_ui.sh`, `config.js` даст 404 в
консоли — не страшно, UI просто возьмёт тот же origin.

## Библиотека фрагментов

Отдельная карточка на странице: клипы, записанные из демок (их присылает
рендер-бэкенд), и свои ролики пользователя в одной сетке. Можно перетащить
файлы мышью или выбрать через диалог, посмотреть превью, переименовать и
удалить; фильтры по источнику и поиск по названию считает сервер.

Своё видео заливается через `XMLHttpRequest`, а не `fetch`: у `fetch` нет
прогресса отправки, а ролики здесь под сотню мегабайт — без полосы непонятно,
идёт загрузка или всё зависло. Несколько файлов уходят по очереди: параллельные
заливки делят один канал, все ползут медленно, а прогресс перестаёт что-либо
значить. Ограничения (расширения, потолок размера) UI не хардкодит — они
приходят в ответе `GET /api/library`.

Фрагменты из демок появляются в библиотеке **асинхронно**: рендер-хост шлёт их
фоном уже после записи, поэтому список обновляется по событиям задачи, а не
только по её завершению.

Названия задаёт человек, поэтому в разметку они попадают только экранированными
— иначе кавычка в имени ломает атрибут, а `<img onerror>` из названия выполнится
как скрипт.

## Что нужно от бэкенда

Бэкенд должен разрешить origin этого UI:

```bash
CS2_CORS_ORIGINS=http://192.168.0.3:8080 ./run_service.sh   # и на рендере, и на библиотеке
```

Иначе браузер заблокирует запросы: `*` там стоит по умолчанию, но сужать его
до адреса своего UI стоит — к API не должна обращаться страница с любого сайта.

С рендер-бэкенда: `GET /api/session`, `GET /api/health`, `GET /api/demos`,
`POST /api/upload`, `GET /api/demo/{id}/players`, `POST /api/jobs`,
`GET /api/events` (SSE), `GET /api/clips/{job}/{file}`,
`POST /api/session/restart`.

С сервиса библиотеки: `POST /api/auth/login`, `GET /api/library`,
`POST /api/library/upload`, `PATCH`/`DELETE /api/library/{id}`,
`GET /api/library/{id}/file`, `GET /api/library/{id}/thumb`.

Ссылки на клипы и ZIP бэкенд отдаёт относительными (`/api/clips/…`), UI сам
достраивает их до адреса бэкенда. Учтите: для другого origin браузер игнорирует
атрибут `download`, поэтому клипы открываются в новой вкладке, а не скачиваются
сразу.
